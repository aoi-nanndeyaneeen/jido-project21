# 開発方針メモ (2026-08-09)

締切が近く、市販フレームの調達（AliExpress 約2週間）が間に合わない前提で組み立てた計画。
結論から言うと **シャシーの再設計はしない。今の機体を補強して、制御ソフトを直す。**

---

## 0. 現状の要約

| 症状 | 状況 |
|---|---|
| モーターの発熱 | 固定治具で冷却が効いていない分 + 制御由来の分が混ざっている |
| 「たらたらたら」振動 | 周波数未測定。ここが分かれば原因が確定する |
| 低スロットルでピクつく、0.5あたりで直る | 補正が出力レンジを超えてクランプに張り付いている |
| マニュアルモードでは問題なし | 姿勢フィードバックが無い＝発振経路が無いため |
| シャシーのねじれ | ペンチで戻して改善の体感あり。寄与はあるが単独原因ではない |

**これまで全部、推測で議論していた。** 実測できるようにしたので、まずログを取る。

## 1. まずやること: ログを取る（実装済み）

`drone.cpp` に 500Hz のロガーを実装した。`scripts/logger.py` のプロトコルに合わせてあるので
スクリプト側の変更は不要。

```
pio run -e drone -t upload
python scripts/logger.py          # 別ターミナル。VSCodeのシリアルモニタは閉じる
# 'L' + Enter で記録開始 / もう一度で停止
python scripts/analyze_log.py --plot
```

記録内容: `dt`, `mode`, `armed`, `thr`, スティック3軸, 姿勢角3軸, ジャイロ3軸,
PID出力3軸, モーター出力4本, `corr_limit`, `sat`（クランプに当たったか）

**取るべきログは3本:**

1. **静止・モーター停止** 10秒 → ジャイロのノイズ下限を知る
2. **固定治具・スロットル0.3前後** 15秒 → 今のピクつきを記録
3. **P/Dをゼロにして同条件** 15秒 → 機体振動と制御発振を切り分ける

`analyze_log.py` が出す **FFTのピーク周波数** で原因がほぼ決まる:

| ピーク | 原因 | 対処 |
|---|---|---|
| 5〜30 Hz | 制御ループの発振 | ゲインを下げる（§3） |
| 30〜80 Hz | シャシーの構造共振 | 機械的な補強（§2） |
| 80 Hz〜 | プロペラ/モーター | バランス取り、IMUの防振 |

シャシーを触るかどうかは、この数字を見てから決める。体感で判断すると必ず遠回りになる。

## 2. シャシー: 再設計しない。補強する

再設計を勧めない理由:

- 制御側に確実な問題が残っている（§3, §4）。同時に動かすと切り分けができなくなる
- 締切に対して、設計 → 出力 → 組み直し のサイクルが重すぎる
- ねじれが主原因なら、補強で十分に検証できる

**やること（1時間以内で済む範囲）:**

- ペンチで戻した状態から、アーム根元に補強材（カーボン角材、アルミアングル、
  タイラップ＋エポキシなど手元にあるもの）を追加してねじれを止める
- 4本のアームの水平を定規で確認する。モーター取付面が傾いていると、
  推力に常時オフセットが乗り、I項が無くても機体が偏り続ける
- プロペラの曲がり・欠けを確認して交換する。壁に当てているなら最有力
- IMUを両面テープ1枚で直付けしているなら、スポンジを挟んで防振する
  （これは80Hz以上のノイズに効く）

**再設計を検討すべきなのは、FFTで30〜80Hzに明確なピークが出て、
補強しても消えなかった場合だけ。**

## 3. ゲイン: 単位が合っていない（最重要）

現在の `drone.cpp`:

```cpp
Axis_value Roll(2.0f, 0.0f, 0.03f, 5.0f, 0.0f, 0.0f, ...)
//              kp_rate  ki  kd_rate  kp_angle
```

`Control.h` の `pidStep()` は `e = tar * kando - input` で、`input` は
**ジャイロの生値 [deg/s]**。出力 `cmd` は最終的にモーターの `0.0〜1.0` レンジに
足し込まれる。つまり `kp_rate` は「deg/s → スロットル比」の変換係数。

`kp_rate = 2.0` だと:

| ジャイロ誤差 | cmd |
|---|---|
| 0.25 deg/s（ほぼノイズ） | 0.50 ← **もうクランプ上限** |
| 5 deg/s | 10.0 |
| 50 deg/s | 100.0 |

MPU6050 は静止時でも 0.1〜0.5 deg/s 程度のノイズが乗る。
**機体が何も動いていなくても出力が振り切れる。** これが観測している症状と符合する。

妥当なオーダー:

```
kp_rate  : 0.002 〜 0.005   （50 deg/s の誤差で cmd 0.1〜0.25）
kd_rate  : 0.00002 〜 0.0001
ki_rate  : 0（P/Dが決まるまで触らない）
kp_angle : 3.0 〜 6.0        ← これは今の 5.0 で妥当。単位が deg → deg/s なので別スケール
```

`kd_rate = 0.03` も同様に過大。D はジャイロを `1/dt` で微分してから掛けるので、
500Hz なら実質 500 倍される。ノイズ増幅の主犯。

**手順:** `kp_rate` を `0.002` に、`kd_rate` を `0.0f` にして、
P だけで振動しない上限を探す。その後 D をごく小さく足す。

## 4. コード側で見つかっている問題

### 🔴 ヨー制御が存在しない

ミキサーは `Roll.cmd` と `Pitch.cmd` しか使っていない。
`Yaw.cmd` は計算されているが**モーターに一切反映されていない**。
機体はヨー方向に何の制御も受けていない。

```cpp
const float raw1 = -Pitch.cmd + Roll.cmd;   // Yaw が無い
const float raw2 =  Pitch.cmd - Roll.cmd;
const float raw3 =  Pitch.cmd + Roll.cmd;
const float raw4 = -Pitch.cmd - Roll.cmd;
```

ホバリングに入ると機首が回り続けるはず。X配置なら対角ペア
（同じ回転方向の2本）に `±Yaw.cmd` を足す。ただし**プロペラの回転方向を
実測してから**でないと符号を間違えて悪化する。

### 🔴 Roll と Pitch で軸が入れ替わっている

```cpp
Roll.update_value (sbus.des[Ch::ROLL],  mpu.getPitch(), mpu.getAccY(), mpu.getGyroY());
Pitch.update_value(sbus.des[Ch::PITCH], mpu.getRoll(),  mpu.getAccX(), mpu.getGyroX());
```

`Roll` に**ピッチ角とY軸ジャイロ**が入っている。IMUが90度回して取り付けてあるなら
正しいが、そうでなければロール指令がピッチを見て動く。
ログの `roll_gyr` を見ながら機体をロール方向に傾けて、値が動くか確認すること。

### 🟡 固定翼モードが生きている

`MODE_LEVEL_TURN` は `Roll.tar = -BANK_ANGLE`（= -25度）を設定する。
スイッチが入るとクアッドが25度バンクを保持しようとする。危険なので削除するか、
少なくとも `BANK_ANGLE = 0` にしておく。

### 🟡 Madgwick のレートが実測と合っていない

`filter.begin(Config::Timing::MAIN_Hz)` で 1000Hz 固定。
I2C で `getMotion6()` を読むだけで 350〜400us かかるため、実ループは
1000Hz に届いていない可能性が高い。ずれていると姿勢角に誤差と遅れが出る。
**ログの `dt_us` で実測できる。** 大きくずれていたら `filter.begin()` に実測値を渡す。

### 🟡 P項にフィルタが無い

`d_alpha` は D項にしか掛かっていない。P項はジャイロの生値を直接使う。
`kp_rate` を正しいオーダーに下げれば大半は解決するが、機体振動が大きい場合は
測定値そのものにローパスを1段入れる必要がある。

### ⚪ その他

- `writeServos()` が空のまま毎ループ呼ばれている
- `resetTiming()` はテンプレート内 static をリセットできない（コメントが自認済み）
- `Ch_state(THR_CUT)==down` と `Receiver.h` の `th_cut()` で規約が逆
- `Receiver.h` の `SbusData _data{}` は初期化済みに修正済み

## 5. 進め方（締切考慮）

**Day 1: 測る**
1. ログを3本取る（§1）
2. `analyze_log.py` を回して FFT ピークと飽和率を確認
3. ここで原因が制御側か機械側かが確定する

**Day 2: 制御を直す**
4. `kp_rate = 0.002` / `kd_rate = 0` に落として再測定
5. 飽和率が数%まで下がることを確認（ここが効いたかの判定基準）
6. 軸の入れ替えをログで確認して修正
7. P → D の順に詰める。各ステップでログを取って残す

**Day 3: 機体とヨー**
8. アーム補強、プロペラ交換、水平出し
9. 回転方向を実測してヨーミキシングを追加
10. 固定翼モードを削除

**判断ポイント:** Day 1 のFFTで 30〜80Hz に強いピークが出て、
補強しても消えないなら、そこで初めてシャシー再設計を検討する。
それ以外なら今の機体で押し切る。

## 6. 「完全自作」に立ち返って

シャシーもFCも自作、という当初の狙い自体は変えなくていい。ただし
**同時に自作すると、問題がどちらにあるか永久に切り分けられない。**

段階的リファクタリング用に `drone_s1` 〜 `drone_s4` を用意してあるのは、
まさにこの切り分けのため（`platformio.ini` に env 追加済み）:

- `s1` 出力段のみ（PIDなし）— 配線・回転方向・THR_CUT の確定
- `s2` X配置ミキサー + センサ軸の確認（PIDなし）
- `s3` レートPID — 初飛行
- `s4` 角度PID + モード切替

今は `drone.cpp` で進めているので無理に移行しなくてよいが、
**`s1` と `s2` の確認項目だけは一度通しておく価値がある。**
特にヨーの回転方向とRoll/Pitchの軸割り当ては、ここで確定していないと
何度でも同じ問題に戻ってくる。

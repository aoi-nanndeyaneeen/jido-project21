## 1. 背景 — なぜこれが必要か

クアッドコプター（`flight_controller`）のヨー方位が確定しない。

- 搭載IMUは **MPU6050 = 6軸（磁気センサなし）**。ヨーはジャイロZの積分でしか得られない
- `IMU.h` は `Madgwick::updateIMU()`（6軸版）を使っており、ヨーに補正項が一切入らない。
  `mpu.getYaw()` は**純積分そのもので、絶対方位としては最初から意味を持たない**
- ジャイロZのバイアスは温度で 0.5〜2 deg/s 動く。0.5 deg/s でも **1分で30度**ずれる
- 磁気センサの追加は検討したが、フレームが小さく（モーターまで9cm）ESC/バッテリー電流の
  磁界が強すぎるため見送り
- 競技フィールドが広くカメラ距離は最大30m、かつ最大広角。**マーカー（ArUco等）は使えない**

### 姿勢制御そのものには絶対方位は不要（対応済み）

機体側は「ヘディングホールド」を実装済みで、**相対**方位を保持することでヨーは安定する。
これは市販フライトコントローラと同じ方式で、積分ドリフトの影響を受けない。

**絶対方位が必要なのは自律位置制御のためだけ**である。カメラが出すフィールド座標系の
位置誤差を、機体のロール/ピッチ指令（機体座標系）に変換するのに、両座標系の間の
回転角＝ヨーが要る。

⚠️ **ここが安全上の急所**: ヨー推定が90度以上ずれていると、位置制御ループが
**正帰還になり機体が飛んでいく**。精度そのものより、大きく外さないことが重要。

## 3. 依頼する作業（position_estimator 側）

**機体から降りてくる「機体座標系の速度変化」と、カメラが測る「フィールド座標系の
速度変化」を照合して、ヨーを算出し、機体へ返す。**

計算は**すべて地上PC側で完結させる**。理由は、カメラ→PC→IM920→機体の遅延
（100〜300ms）を、両方の信号が揃っているPC側で時刻合わせして吸収するのが
圧倒的に楽だから。上りリンクにはスカラー1個だけ流す。

```
[機体] 200ms ごとに、機体座標系の Δv + タイムスタンプ を下り送信 (5Hz)
          ↓ IM920
[地上PC] ★ここが依頼範囲★
         カメラの速度履歴と時刻を合わせ、1秒窓の Δv を比較してヨーを算出
         ゲートと平均化をかける
          ↓ IM920
[機体] 受け取ったヨーで g_yaw_est / g_yaw_hold を弱いゲインで補正 (0.5〜1Hz)
```

## 4. アルゴリズム仕様

### 4-1. 原理

クアッドは**傾いた方向に加速する**。機体は自分の roll/pitch を正確に知っている
（加速度計で補正されるためヨーと違ってドリフトしない）ので、
**「機体座標系での加速度方向」は既知**。カメラは
**「フィールド座標系での加速度方向」**を測れる。この2つのベクトルのなす角がヨーである。

```
ψ = atan2(フィールド系Δvのy, x) − atan2(機体系Δvのy, x)
```

ArduPilot EKF3 が磁気センサなしで飛ぶときに使う GSF (Gaussian Sum Filter)
yaw estimator と原理的に同じ、実績のある手法。

### 4-2. ⚠️ 速度ベクトルではなく「速度の変化」を使うこと

`src/core/autopilot.py:195` の現在の実装:

```python
if horiz_speed > self.MIN_SPEED_FOR_HEADING:
    self.heading = math.atan2(vy, vx)      # ← 固定翼の仮定
```

これは**飛行機のコード**である。飛行機は横滑りしないので進行方向＝機首方向だが、
**クアッドは真横にも真後ろにも飛べる**ので進行方向と機首方向は一致しない。
クアッドではこの式は使えない。必ず Δv（速度の変化）で照合すること。

### 4-3. ノイズ処理

30m先を広角で見た位置推定を2階微分するのは不可能。**Δv マッチング**にする。

粗い見積もり（位置ノイズ σ ≈ 0.2m 想定）:

| 段階 | 誤差 |
|---|---|
| 1秒窓で速度を算出 | σ_v ≈ 0.28 m/s |
| 1秒間の Δv | σ ≈ 0.4 m/s |
| 実 Δv が 2 m/s のときの角度誤差 | atan(0.4/2) ≈ **11度**（1回あたり） |
| 10回平均 | **3〜4度** |

毎回正確な方位は取れないが、**0.5〜2 deg/s のジャイロバイアスを抑えるには十分**。
目的に対して精度は足りている。

### 4-4. 実装手順

1. `tracker.py` の3D位置履歴から、**1秒窓の移動平均で速度**を出す
   （既存 `main_loop.py:150` 付近の `vel_ap`（2点差分）はオートパイロット用で
   ノイズが大きすぎる。ヨー推定には別系統の平滑化した速度を用意すること）
2. 機体から届いた `(t_ms, dvx_body, dvy_body)` をリングバッファに貯める
3. 同じ時刻窓のカメラ側 Δv を取り出す（**時刻合わせが肝**。§5-3 参照）
4. **ゲート**: 以下を満たさない窓は捨てる
   - `|Δv_camera| < 1.0 m/s` → 方向が純ノイズになるため
   - `|Δv_body| < 1.0 m/s` → 同上
   - `| |Δv_camera| − |Δv_body| | / |Δv_camera| > 0.5` → 大きさが合わない＝どちらかが異常
   - カメラのトラッキングが `PixelJumpFilter` / residual フィルタで棄却された区間を含む
   - ダミー円軌道フォールバック中（30フレーム未検出時）
5. 生のヨー測定値を算出し、**円形平均**で移動平均を取る
   （`atan2(mean(sin θ), mean(cos θ))`。単純平均は±180°をまたぐと壊れる）
6. 連続 N 回（推奨 5回）が互いに ±20度以内に収まったら「収束」とみなし、
   `yaw_valid = 1` を立てて送信開始

### 4-5. 頻度

| 経路 | 頻度 | 根拠 |
|---|---|---|
| 下り（機体→PC）Δv | **5 Hz**（200ms窓） | 1秒窓を5サンプルで構成できる |
| PC内部の照合 | 1 Hz（1秒窓を0.2秒ずつスライド） | — |
| 上り（PC→機体）ヨー | **0.5〜1 Hz** | 補正対象は 1 deg/s 程度のドリフトのみ。収束時定数 5〜10秒を狙えば足りる |

**上りを速くしても損しかしない。** 通信ジッタが姿勢に乗るだけ。

## 5. プロトコル仕様

### 5-1. 既存の構造体

`flight_controller/include/Config.h` と `ground_receiver/include/Config.h` に
**完全に同一の定義**が置かれている（片方だけ直すと壊れる）。
IM920SL の実効ペイロード上限は 60 bytes。

```c
struct __attribute__((__packed__)) PlaneData {     // 機体 → 地上
    float ax, ay, az;        // 加速度 [g]  ※機体座標 FLU (前・左・上)
    float roll, pitch, yaw;  // 姿勢角 [deg]
    float altitude;          // 高度 [m]
};                           // 28 bytes（上限60。余裕32）

struct __attribute__((__packed__)) GroundData {    // 地上 → 機体
    float p_adj, i_adj, d_adj;
    float roll, pitch, yaw;
    uint8_t reset_cmd;
    uint8_t param_sel;
    float ap_roll, ap_pitch, ap_yaw;
    float ap_throttle;
};                           // 42 bytes（上限60。余裕18）
```

※ `ground_receiver/include/Config.h:9` のコメントは `PlaneData: 4 + 8*4 = 36 bytes`
となっているが、実際の構造体は float 7個 = **28 bytes**。コメントが古い。

### 5-2. 追加するフィールド（提案）

**PlaneData に追加**（28 → 40 bytes、上限内）:

```c
    uint32_t t_ms;    // 機体の millis()。Δv窓の終端時刻
    float dvx_body;   // 直近200msの速度変化 [m/s] 機体前方向 (+X)
    float dvy_body;   // 直近200msの速度変化 [m/s] 機体右方向 (+Y)
```

`dvx/dvy` は機体側で「加速度計の比力から重力を引いて水平成分を取り出し、
200ms 積分したもの」。**ヨーだけが未知の座標系**（機体のヨー推定を基準とした水平面）で
表現されている。

**GroundData に追加**（42 → 47 bytes、上限内）:

```c
    float   yaw_abs;    // フィールド座標系での機首方位 [deg]
    uint8_t yaw_valid;  // 0=無効(機体は無視), 1=有効
```

### 5-3. 時刻合わせ

機体の `millis()` とPCの時刻は同期していない。**オフセットを1回推定して固定する**:

1. 最初の数パケットで `offset = t_pc_受信時刻 − t_ms` を取り、中央値を採用
2. 受信遅延のばらつき（IM920 のリトライ等）があるので、**最小値**を使うほうが安定
   （最小遅延のパケットが最も真値に近い）
3. Teensy の `millis()` はドリフトするが、数分の競技時間なら無視できる

### 5-4. 経路

`position_estimator` は `ground_receiver`（`main_pc.cpp`）と USB シリアルで繋がっている。
`src/core/communication.py` の `SerialReceiver` が窓口:

- **受信**: `_receive_loop()` が `"DATA,"` 行をパースしている。
  `ground_receiver` 側に Δv を出す行を追加してもらい、ここでパースする
- **送信**: `send_autopilot_command()` が `"AP,roll,pitch,yaw,throttle\n"` を送っている。
  同じ形式で `"YAW,<yaw_deg>,<valid>\n"` を追加するのが素直

**`ground_receiver/src/main_pc.cpp` の改修も必要**（`GroundData` 構造体の更新と、
新しいシリアル行の解釈）。ここは flight_controller 側と歩調を合わせること。

## 6. 運用シーケンス（フィールドでの手順）

ユーザーが想定している競技運用:

### ① 初期アラインメント（アーム時）

**機体をフィールドの既知方向に向けて配置し、その方位を初期値として与える。**

これが一番安く効く。`g_yaw_est` の初期値が数度の精度で決まるので、カメラ側は
**「絶対値をゼロから探す」必要がなくなり、ドリフトを補正するだけの役割**になる。
§1で述べた「90度ずれて飛んでいく」リスクがほぼ消える。

### ② 進入フェーズ ＝ 最初の較正機会

競技開始後、**機体はまっすぐ前進してカメラの画角内に入る。**

これは偶然にも**ヨー較正に理想的な機動**である:

- 純粋な前進加速 → `Δv_body` は +X 方向のみ、`dvy_body ≈ 0`
- 加速が大きい → S/N が高い
- カメラ側で観測される Δv の方向が、**そのまま機首方位**

**この区間を「最初の絶対ヨー確定」として最優先で使うこと。**
`|Δv|` が大きくゲートを確実に通るので、ここで数回の測定を平均すれば
数度の精度でヨーが確定する。

実装上は、「進入フェーズ中は `dvy_body ≈ 0` を前提にした簡易版
（ψ = atan2 of camera Δv のみ）」を別ルートで用意すると、より頑健になる。

### ③ 巡航中

適宜リセット（＝補正を継続的にかけ続ける）。ホバリング中は加速度がなく
**ヨーが観測できない**ので、機動している間だけ測定が入る間欠的な補正になる。
これで問題ない。ジャイロ積分が間を埋める。

### ④ 自律位置制御を閉じるタイミング

**カメラ由来の測定が N 回連続で整合するまで、位置制御ループを閉じない**ゲートを入れること。
`yaw_valid` フラグの役割はこれ。

## 7. 機体側の融合（参考。flight_controller 側で実装する）

```cpp
const float CORR_GAIN = 0.02f;              // 弱く
float diff = wrap180(yaw_abs - g_yaw_est);
g_yaw_est  += CORR_GAIN * diff;
g_yaw_hold += CORR_GAIN * diff;             // ★ 目標も同量ずらす
```

`g_yaw_hold` も一緒に動かすのが肝。こうすると「推定値の座標系がゆっくり
絶対座標へ合っていく」だけで、**保持している物理的な向きは動かない** →
補正が入っても機体が振れない。**レートループには絶対に入れない。**

## 7-2. ⚠️ `ap_yaw` は「ヨーを動かしたくないとき厳密に 0.0」を送ること

機体側のヘディングホールドは、**ラダー入力の有無で挙動が切り替わる**:

```cpp
const bool yaw_stick_active = (fabsf(yaw_axis.stick) > 0.03f);  // YAW_STICK_DEAD
if (yaw_stick_active) {
    // レート指令モード。保持目標は現在値に追従（＝保持しない）
} else {
    // ヘディングホールド。方位を保持する
}
```

`MODE_AUTO` では `yaw_axis.stick = g.ap_yaw` になる。つまり
**地上局が `ap_yaw` に 0.03 を超えるノイズを乗せ続けると、ヘディングホールドが
永久に無効化される。** 機首がじわじわ回り出すが、原因が地上局側にあるため
機体を見ても分からない。

対策:

- ヨーを積極的に指令しないときは **厳密に `0.0` を送る**（PID出力をそのまま流さない）
- 地上局側でも不感帯を入れる（`abs(yaw_cmd) < 0.05` なら `0.0` に丸める）
- `RCCommand.yaw` は `src/core/autopilot.py:35` で `現状未使用` とコメントされており、
  既定 `0.0` のはず。ヨー制御を実装する際にこの点を踏むこと

## 8. 事前に決めておく必要があること → ✅ 確定済み

### 8-1. フィールド座標系 【確定】

`src/utils/config.py` で定義:

```
x = 幅方向（右）   -13 〜 +13 m
y = 奥行方向（奥） -21 〜 +21 m     ※カメラ2台は y = -21 側の2隅
z = 高さ（上）
原点 = フィールド中央の床面。右手系 (x × y = +z)
```

### 8-2. ヨーの定義と符号 【確定】

```
psi = atan2(nx, ny)        n = 機首方向の水平単位ベクトル

  psi =    0 度 → 機首がフィールド奥 (+y)   ※カメラから見て奥向き
  psi =  +90 度 → 機首がフィールド右 (+x)
  psi = ±180 度 → 機首が手前 (-y、カメラ側)
  psi =  -90 度 → 機首がフィールド左 (-x)
```

**+y を北とみなした方位角**そのもの。上から見て**時計回りが正**であり、
機体側の「右へ首を振るのが +」（`quad/QuadConfig.h §1`）と符号が一致する。

> ⚠️ **`atan2(y, x)` ではなく `atan2(x, y)`**。
> 逆にすると回転方向が反転し、位置制御ループが正帰還になる。
> `src/core/yaw_estimator.py` の `bearing_deg()` がこの定義の唯一の実装。

導出（`yaw_estimator.py` 冒頭にも記載）:

```
機体前方 n = (nx, ny)、機体右方 r = (ny, -nx)
Δv_field = dvx_body · n + dvy_body · r
両辺の方位角をとって   bearing(Δv_field) = psi + atan2(dvy_body, dvx_body)
∴  psi = bearing(Δv_field) − atan2(dvy_body, dvx_body)
```

### 8-3. Δv の座標系 【確定 — 機体側で変換して送る】

`DV,` 行で送る `dvx_body` / `dvy_body` は **FRD の (前, 右)** [m/s]。

`IMU.h` の `getAccX/Y/Z` は **FLU（前・左・上）** を返すので、
**機体側で FRD に変換してから送ること**（`dvy_body = -（FLUのY成分）`）。
PC側では一切変換しない。

### 8-4. 初期アラインメント 【確定 — PC側の config で持つ】

`src/utils/config.py` の `YAW_INITIAL_ALIGN_DEG`（既定 `0.0` ＝
機首をフィールド奥 +y へ向けて置く）。

- オートパイロットはヨー未確定のあいだ、この値を保持する
  （速度ベクトルからは推定しない）
- `YAW_SEND_INITIAL_ALIGN = True` のとき、未収束中もこの値を
  `valid=0` で送り続ける。**機体側は `valid=0` を完全に無視すること**

アーム時に別の向きで置くなら、この定数を書き換える。

## 10. 他リポジトリ側への依頼（契約）

position_estimator 側は完成しているので、以下が揃えば動く。

### 10-1. `flight_controller` — PlaneData に3フィールド追加

```c
    uint32_t t_ms;    // 機体の millis()。Δv窓の終端時刻
    float dvx_body;   // 直近200msの速度変化 [m/s] 機体 前(+X)  ※FRD
    float dvy_body;   // 直近200msの速度変化 [m/s] 機体 右(+Y)  ※FRD
```

28 → 40 bytes（上限60内）。`ground_receiver/include/Config.h` と**完全に同一**にすること。

- 加速度計の比力から重力を引き、水平成分を 200ms 積分した値
- **FLU→FRD の変換は機体側で行う**（§8-3）
- 送信頻度 **5 Hz**

### 10-2. `flight_controller` — GroundData に2フィールド追加

```c
    float   yaw_abs;    // フィールド座標系での機首方位 [deg]（§8-2 の定義）
    uint8_t yaw_valid;  // 0=無効（機体は完全に無視すること）, 1=有効
```

融合は §7 のとおり弱いゲインで。**レートループには絶対に入れない。**

### 10-3. `ground_receiver/src/main_pc.cpp` — シリアル2行

**出力**（PC が読む）:

```
DV,<t_ms>,<dvx_body>,<dvy_body>\n
```

例: `DV,123456,0.412,-0.087`
`PlaneData` を受信するたびに1行出す。既存のダッシュボード表示とは別行にすること。

**入力**（PC から届く。既存の `AP,` と同じ要領で解釈）:

```
YAW,<yaw_deg>,<valid>\n
```

例: `YAW,-37.42,1`
受信した値を `GroundData.yaw_abs` / `yaw_valid` に入れて機体へ転送する。
到着頻度は 1 Hz。

> 既存の `Att: Roll=.. Pitch=.. Yaw=..` 表示行も PC 側で解析している
> （旋回中の窓を捨てるゲート用）。この行の書式は変えないこと。

## 9. 受け入れ基準

- 進入フェーズの直進機動で、ヨー測定値が **±10度以内**で5回連続して一致する
- ホバリング中は `yaw_valid` が立たない（＝加速度がないときに嘘の値を出さない）
- カメラロスト／ダミー円軌道フォールバック中は `yaw_valid` が立たない
- 機体側のジャイロ積分ヨーと、カメラ由来ヨーの差が、
  30秒以上の飛行で **±15度以内**に収まり続ける
